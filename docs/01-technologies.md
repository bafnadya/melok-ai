# Применяемые технологии и решения

## Архитектура
Приложение работает по схеме «клиент — сервер». Учитель вводит данные в браузере, сервер обрабатывает их по правилам, а результаты сохраняются в базе данных.

Поток данных: **Браузер → Серверное API → Модуль правил → База данных → Выдача результата пользователю.**

## Стек технологий

| Средство | Назначение | Роль в проекте |
| :--- | :--- | :--- |
| **HTML, CSS, JavaScript** | Браузерный интерфейс | Ввод описания задач, заполнение анкеты условий, просмотр истории и отчётов. Не требует установки отдельного мобильного приложения. |
| **Python и FastAPI** | Серверная обработка | Выполнение логики правил оценки, валидация входных данных, связывание формы пользователя и аналитического модуля через API. |
| **SQLite и sqlite3** | Хранение данных | Локальное хранение задач, ответов, версий правил и результатов оценки. Не требует развертывания отдельного сервера СУБД, что оптимально для малого пилота. |
| **CSV** | Экспорт данных | Выгрузка записей и результатов для дальнейшего анализа и подготовки протоколов испытаний. |
| **unittest** | Тестирование | Проверка корректности работы правил и обработки входных данных средствами стандартной библиотеки Python. |
| **Git и удалённый репозиторий** | Контроль версий | Учёт изменений кода, правил и документов, обеспечение прослеживаемости вклада участниц команды. |

## Модель данных
В базе хранятся четыре основные сущности:
1. **Задача** — описание рабочей операции учителя.
2. **Ответы** — данные из анкеты условий.
3. **Правило** — условие с уникальным ID и версией.
4. **Результат** — итоговая категория, объяснение и ссылка на версию правила.

*Важно:* если правила обновляются, старые результаты не меняются автоматически. Это нужно для прозрачности.


## Ограничения
* Нет интеграции с электронным журналом.
* Система не выполняет задачи за учителя и не проверяет работы учеников.
* Текст, написанный пользователем, не является единственным основанием для решения — систему нужно подтверждать.
