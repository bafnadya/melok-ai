# Применяемые технологии и решения

## 1. Архитектура приложения

Приложение планируется реализовать по клиент-серверной архитектуре. Учитель взаимодействует с системой через браузер: вводит описание рабочей задачи, заполняет анкету условий и просматривает результаты. Сервер принимает запросы, проверяет структуру и корректность входных данных, передаёт их модулю правил, сохраняет необходимые сведения в базе данных и возвращает результат пользователю.

| Элемент | Назначение |
| :--- | :--- |
| **Браузерный интерфейс** | Ввод и редактирование описания задачи, заполнение анкеты, просмотр результатов, истории и отчётов. |
| **Серверное API** | Приём запросов от интерфейса, проверка структуры входных данных и передача их соответствующим компонентам приложения. |
| **Модуль правил** | Проверка смысловой согласованности ответов и применение формализованных правил оценки. |
| **База данных** | Хранение задач, ответов, версий правил и результатов оценки. |
| **Возврат результата** | Передача пользователю итоговой категории, пояснения и информации о необходимости уточнения данных. |

**Поток данных:** Браузер → Серверное API → Проверка входных данных → Модуль правил → База данных → Возврат результата пользователю.

Разделение интерфейса и серверной логики позволяет изменять правила оценки независимо от пользовательского интерфейса. Централизованное выполнение правил также упрощает обеспечение единообразия результатов. При этом одинаковый результат при повторном запуске гарантируется только при неизменности входных данных, версии правил, версии программного модуля и используемых настроек.

Технологии используются для ввода описания задач, заполнения анкеты, просмотра истории и отчётов. Браузерный интерфейс не требует установки отдельной клиентской программы [7]. |

Смысловая проверка противоречий выполняется отдельной логикой приложения. |

## 3. Обоснование выбора технологий и архитектурных решений

**1. Клиент-серверная архитектура**
Архитектура выбрана для разделения пользовательского интерфейса, серверной обработки и хранения данных. Такое разделение упрощает сопровождение приложения: изменение алгоритмов оценки не требует обязательной переработки интерфейса. Серверное выполнение правил позволяет централизованно применять одну и ту же логику к поступающим запросам.

**2. HTML, CSS и JavaScript**
Эти технологии являются базовыми средствами разработки веб-интерфейсов. Они позволяют создавать формы, элементы навигации, страницы результатов и историю оценок. Использование браузера снижает требования к рабочему месту пользователя: не требуется устанавливать отдельную клиентскую программу, хотя серверную часть приложения необходимо развернуть и запустить.

**3. Python и FastAPI**
Python выбран благодаря читаемому синтаксису и наличию средств для обработки структурированных данных и реализации алгоритмов. FastAPI подходит для создания API и проверки структуры входящих запросов. Это позволяет отделить техническую проверку формата данных от предметной логики: например, проверка обязательности полей выполняется на уровне моделей данных, а выявление смысловых противоречий — отдельными правилами приложения.

**4. SQLite**
SQLite выбрана из-за простоты развёртывания и отсутствия необходимости устанавливать отдельный сервер СУБД. Она позволяет хранить данные в структурированном виде и использовать SQL-запросы для их получения и изменения. Для пилотной версии с одним локальным сервером и небольшим числом задач такое решение может быть достаточным при невысокой нагрузке и ограниченном количестве одновременных операций записи.

**5. CSV**
CSV выбран как простой формат обмена табличными данными. Его можно открыть во многих табличных редакторах и использовать для дополнительного анализа. В выгрузку целесообразно включать идентификатор задачи, дату оценки, итоговую категорию и сведения о применённой версии правила.

**6. unittest и ручное тестирование**
Автоматизированные тесты позволяют многократно проверять отдельные функции при изменении программного кода. Ручная проверка дополняет их оценкой пользовательского интерфейса и последовательности взаимодействия с системой. Совместное применение двух подходов помогает выявлять как ошибки алгоритмов, так и проблемы пользовательских сценариев.

**7. Git и удалённый репозиторий**
Контроль версий необходим для совместной разработки и фиксации изменений кода, правил и документации. История коммитов позволяет анализировать развитие проекта и при необходимости восстанавливать предшествующие состояния. Достоверность сведений об авторстве зависит от корректной настройки учётных записей и дисциплины работы с репозиторием.

## 4. Модель данных

В базе данных предусматриваются четыре основные сущности. Их разделение позволяет хранить сведения об исходной задаче, ответах пользователя, применяемых правилах и полученных результатах отдельно, сохраняя связи между ними.

| Сущность | Содержание | Особенности хранения |
| :--- | :--- | :--- |
| **Задача** | Описание рабочей операции учителя. | Исходная и уточнённая формулировки хранятся под одним идентификатором. |
| **Ответы** | Данные, полученные из анкеты условий. | Сохраняются как исходные данные, на основании которых выполняется оценка. |
| **Правило** | Формализованное условие оценки. | Имеет уникальный идентификатор и номер версии. Опубликованные версии правил не изменяются задним числом. |
| **Результат** | Итоговая категория и объяснение. | Содержит ссылку на конкретную версию правила, снимок ответов пользователя и сведения о версии программного модуля оценки. |

Связи между сущностями рекомендуется реализовать с помощью первичных и внешних ключей. Для одной задачи допускается хранение нескольких результатов оценки. Каждый результат должен быть связан с конкретной версией правила; повторная оценка создаёт новую запись и не перезаписывает предыдущую.

## 5. Сохранение истории и воспроизводимость результатов

Наличие номера версии правила само по себе не гарантирует возможность воспроизвести ранее полученный результат. Для последующей проверки необходимо сохранять не только ссылку на версию правила, но и неизменяемое содержимое этой версии либо ссылку на архивную запись, которую нельзя редактировать задним числом.

Для каждого результата предусматривается сохранение следующих сведений:
* идентификатор задачи и дата выполнения оценки;
* снимок ответов пользователя, использованных при оценке;
* итоговая категория и сформированное объяснение;
* идентификатор и версия применённого правила;
* версия программного модуля оценки и, при необходимости, значимые настройки.

При повторной оценке создаётся отдельная запись. Предыдущий результат сохраняется без изменений. Такой подход обеспечивает прослеживаемость и позволяет установить, какие ответы, правила и версия программной логики использовались при формировании конкретного результата. Полная техническая воспроизводимость дополнительно зависит от неизменности алгоритма и среды выполнения.

## 6. План функционального тестирования

Для проверки пилотной версии предлагается использовать следующие 10 функциональных сценариев. Таблица представляет план испытаний; она не является подтверждением того, что сценарии уже выполнены и успешно пройдены.

| № | Сценарий | Ожидаемый результат |
| :--- | :--- | :--- |
| 1 | Ввод корректного описания задачи | Данные принимаются и сохраняются. |
| 2 | Отправка пустой формы | Система сообщает о необходимости заполнить обязательные поля. |
| 3 | Заполнение анкеты условий | Ответы сохраняются и связываются с соответствующей задачей. |
| 4 | Применение подходящего правила | Формируется результат с категорией и объяснением. |
| 5 | Отсутствие подходящего правила | Система предлагает уточнить данные или направляет случай на экспертную проверку. |
| 6 | Противоречивые ответы | Система выявляет противоречие по заданным проверкам и запрашивает уточнение. |
| 7 | Сохранение результата | Результат появляется в истории оценок. |
| 8 | Повторная оценка задачи | Создаётся новая запись, предыдущая не изменяется. |
| 9 | Просмотр предыдущего результата | Отображается сохранённая оценка с применённой версией правила. |
| 10 | Экспорт результатов | Формируется CSV-файл с предусмотренными полями. |

Автоматизированные тесты unittest целесообразно направить на проверку отдельных функций и правил, а ручные сценарии — на проверку интерфейса, переходов между страницами и отображения сообщений об ошибках.

## 7. Технические ограничения

| Ограничение | Описание |
| :--- | :--- |
| **Интеграции** | В пилотной версии не предусматривается интеграция с электронным журналом и внешними системами школы. |
| **Функциональные границы** | Система не выполняет задачи за учителя и не обрабатывает работы учеников. Она предназначена для аналитической поддержки принятия решений. |
| **Использование свободного текста** | Свободный текст не является единственным основанием решения. Значимые признаки подтверждаются пользователем посредством анкеты или уточняющих вопросов. |
| **Область применимости** | Выводы ограничены каталогом проверенных сценариев. Нестандартные случаи направляются на уточнение или экспертную проверку. |
| **Эксплуатация и нагрузка** | SQLite рассчитана на предполагаемый небольшой масштаб пилотной версии. При росте числа пользователей и интенсивности одновременной записи архитектуру хранения необходимо повторно оценить. |
| **Защита данных** | Поскольку приложение хранит пользовательские ответы и результаты, при реализации необходимо определить права доступа, порядок резервного копирования и меры защиты локальной базы данных. |

## 8. Итоговое обоснование выбранного решения

Выбранный технологический стек соответствует задачам пилотной версии приложения. HTML, CSS и JavaScript обеспечивают браузерный интерфейс; Python и FastAPI — серверную обработку и взаимодействие компонентов; SQLite — локальное хранение структурированных данных. CSV обеспечивает экспорт, unittest и ручные сценарии — проверку программной логики и пользовательских операций, а Git — контроль изменений в ходе разработки.

Архитектура и модель данных предусматривают разделение задач, ответов, правил и результатов. Сохранение снимка ответов, итогового объяснения, версии правила и версии программного модуля позволяет повысить прозрачность и прослеживаемость оценок. При этом корректность конкретных результатов должна подтверждаться тестированием реализованного приложения.

Таким образом, выбранные технологии и решения являются обоснованными для создания пилотной версии при заявленных ограничениях. Дальнейшее расширение проекта может потребовать пересмотра средств хранения данных, механизмов доступа и интеграции с внешними системами.
